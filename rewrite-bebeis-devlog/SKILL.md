# 개발로그 말투 교정

기술적 사실과 판단은 보존하고 문체와 글의 흐름을 작성자의 목소리로 다듬는다. 문제 해결 경험을 이해하는 데 필요한 배경 설명과 그림을 보완할 수 있다. 맞춤법 오류나 습관적인 중복까지 흉내 내지는 않는다.

작업 전에 [말투 기준](references/voice-profile.md)을 전부 읽는다.

사용자가 편집을 명시적으로 요청한 문서만 수정한다. 말투 분석이나 스킬 생성 요청만으로 원문과 기존 README를 수정하지 않는다.

## 작업 순서

1. 사용자가 수정 대상으로 지정한 문서를 확인한다. 같은 사례의 README와 링크된 원문 블로그는 말투와 사실을 확인하기 위해 읽을 수 있지만, 수정 범위로 자동 포함하지 않는다.
2. 수정 전에 보존할 항목을 내부적으로 정리한다. 수치, 측정 조건, 기술적 주장, 실패 결과, 버전 순서, 링크, 코드 식별자, 파일 경로가 여기에 해당한다.
3. 문서의 역할을 구분한다. 사례 README는 문제와 개선 흐름을 설명하고, 버전 README는 해당 단계의 차이와 읽을 코드를 설명한다. 같은 설명을 여러 문서에 반복하지 않는다.
4. 문제, 관찰, 선택의 근거, 결과가 이어지도록 글의 흐름을 정리한다. 다음 판단에 필요한 배경지식과 세부 절의 이해를 돕는 그림은 아래 기준에 따라 필요한 지점에 배치한다.
5. 문단 단위로 고친다. 한 문단에는 가급적 하나의 사실이나 판단만 둔다. 사실을 먼저 쓰고 필요한 이유나 선택 기준을 바로 잇는다.
6. 전체 문서를 다시 읽으며 앞에서 설명한 결론, 작위적인 서사, 문서 제작 과정에 대한 메타 설명을 삭제한다.
7. 원문과 diff를 비교해 보존 항목이 바뀌지 않았는지 확인한다. `git diff --check`와 로컬 Markdown 링크 검사를 수행한다. 추가한 그림도 본문과 사실이 일치하고 게시 환경에서 표시되는지 확인한다.

## 변환 원칙

- 평어체 `~다`, `~했다`, `~라고 판단했다`를 사용한다.
- 짧고 직접적으로 쓴다. 다만 모든 문장을 같은 길이로 잘라 리듬을 기계적으로 만들지는 않는다.
- 구현 사실과 작성자의 판단을 구분한다. 근거가 있는 선택에는 `나는`, `우리 팀은`, `생각했다`, `판단했다`를 쓸 수 있다.
- `사실`, `다만`, `물론`, `내 경험상`, `좀`은 문맥에 맞을 때만 사용한다. 작성자다운 표현이지만 장식처럼 추가하지 않는다.
- 괄호 속 사담이나 `ㅎㅎ`는 원문에 실제 경험이나 농담이 있을 때만 살린다. 새 감정이나 경험을 만들지 않는다.
- 소제목은 명사형을 우선한다. 질문형이나 문장형 소제목은 내용상 꼭 필요할 때만 사용한다.
- 불릿은 순서, 조건, 수치 비교처럼 목록 자체에 의미가 있을 때만 둔다. 설명 문단을 습관적으로 불릿으로 쪼개지 않는다.
- 문제 해결의 핵심 시퀀스가 문장만으로 잘 드러나지 않으면 실제 저장소 코드를 짧게 발췌해 코드 블록으로 넣을 수 있다. 이때 [코드 발췌 기준](references/code-excerpts.md)을 전부 읽고 따른다.
- 기존 코드 블록은 기술적 의미를 보존한다. 말투 교정과 무관한 이유로 코드를 고치지 않는다.
- 링크, 이미지, 표, 코드 식별자와 전문 용어는 보존한다. 표의 설명 문구만 자연스럽게 고칠 수 있다.

## 글의 흐름과 배경지식

- 기술이나 설정을 단순히 나열하지 않고, 실제로 겪은 문제와 관찰, 검토한 선택지, 선택 이유, 확인된 결과를 연결해 경험을 공유한다. 원문에 없는 고민이나 사건을 만들거나 모든 글을 같은 목차에 끼워 맞추지는 않는다.
- 절 사이의 연결은 앞선 관찰이 다음 판단에 어떤 근거가 되는지로 드러낸다. 전환을 예고하는 문장 대신 사실과 판단을 바로 적는다.
- 배경지식은 다음 결정을 이해하는 데 필요한 범위까지만, 해당 판단 가까이에 설명한다. 독자가 이미 읽은 설명은 반복하지 않는다.
- 용어를 사전처럼 나열하지 않는다. 이번 결정에 필요한 항목을 골라 구체적으로 설명한다: 개념이 실제로 나타내는 값이나 범위와 단위, 비슷한 개념과의 차이, 운영 환경에서 이어질 수 있는 문제, 이번 설정을 정하는 데 필요한 이유.
- 배경 설명과 그림의 기술적 근거는 원문, 실제 코드 또는 확인한 출처에서 확보한다. 확인되지 않은 동작, 수치, 운영 경험을 보충하지 않는다.

## 세부 절을 돕는 그림

- 문장만으로 관계나 차이를 파악하기 어려운 지점에 그림을 넣는다. 한 그림은 인접한 세부 절의 한 가지 개념, 비교 또는 판단만 다룬다. 글 전체나 여러 절을 한 그림에 담지 않는다.
- 도형과 화살표, 구조도, 비교도, 그래프 등 설명 대상에 맞는 표현을 고른다. 그림 안의 글은 짧은 라벨, 필요한 수치와 단위 정도로 줄이고 긴 설명은 본문에 둔다.
- 플로우 차트는 지양한다. 호출 순서나 시간에 따른 상호작용이 이해에 꼭 필요할 때만 시퀀스 다이어그램을 사용한다. 구조나 값의 비교를 보여줄 때는 순서도로 바꾸지 않는다.
- 그림은 관련 설명 가까이에 배치하고, 필요한 경우 무엇을 읽어야 하는지 짧은 캡션을 붙인다. 장식용 그림이나 본문을 그대로 옮긴 그림은 추가하지 않으며, 모든 절에 억지로 넣지 않는다.
- 그래프에는 확인된 데이터만 쓰고 축, 단위, 비교 조건을 드러낸다. 개념적 도식은 실측 결과처럼 보이지 않게 구분한다.
- 게시 환경에서 지원하는 다이어그램 문법이나 이미지 형식을 사용한다. Markdown 이미지에는 내용을 식별할 수 있는 대체 텍스트를 넣고 파일 경로를 확인한다.

## Markdown 구성

- 제목 단계로 글의 흐름을 드러내고, 비교는 표, 순서나 조건은 목록, 식별자와 설정값은 인라인 코드로 표현한다. 설명과 판단은 짧은 문단으로 잇는다.
- 코드 블록에는 언어를 지정하고, 핵심 판단에만 제한적으로 강조를 쓴다. 표, 불릿, 굵은 글씨로 본문 전체를 채우지 않는다.

## 금지 사항

- `그런데 바로 다음 질문에서 멈췄다`, `여기서 문제가 발생했다`, `결국 우리는 고민에 빠졌다`, `이제 본격적으로 알아보자`, `과연 이 설정이 맞을까?`, `중요한 것은 바로 이것이다` 같은 작위적인 서사를 쓰지 않는다.
- `이를 통해`, `본질적으로`, `핵심적으로`, `주목할 만하다`, `~할 수 있었다` 같은 AI식 연결과 추상적인 평가를 반복하지 않는다.
- 서론, 본문, 결론에서 같은 결론을 되풀이하지 않는다.
- 독자가 앞에서 읽은 문제를 해결 절과 결과 절에서 다시 풀어 쓰지 않는다.
- 글을 `문제 제기 → 긴장 고조 → 극적인 해결` 서사로 꾸미지 않는다. 사실과 판단을 바로 쓴다.
- 문서가 코드를 선별·재구성·리팩토링해서 만든 결과라는 제작 과정을 본문에 적지 않는다.
- 실제 저장소에 없는 코드를 새로 만들거나 여러 구현을 합쳐 실제 코드처럼 제시하지 않는다.
- 출처에 없는 동기, 감정, 회고, 팀의 합의나 1인칭 경험을 추가하지 않는다.
- 일부러 오탈자, 띄어쓰기 오류, 잘못된 외래어 표기, 과도한 쉼표를 복제하지 않는다.

## 검증 기준

- 모든 문장의 종결이 평어체로 일관되는가.
- 각 문단이 하나의 판단을 다루는가.
- 소제목이 불필요한 문장형·질문형이 아닌가.
- 같은 결론이나 원인 설명이 반복되지 않는가.
- 금지한 서사 문구와 비슷한 표현이 남아 있지 않은가.
- 수치, 링크, 코드, 버전 순서와 기술적 의미가 원문과 같은가.
- 작성자의 실제 경험과 판단만 1인칭으로 표현했는가.
- 기술과 설정의 나열에 그치지 않고 문제, 관찰, 판단, 결과의 관계가 드러나는가.
- 배경지식이 다음 결정을 이해하는 데 필요한 만큼만 구체적으로 설명돼 있는가.
- 각 그림이 인접한 세부 절의 한 가지 내용을 적은 글로 보여주는가. 불필요한 플로우 차트나 시퀀스 다이어그램이 없는가.
- Markdown 구조와 추가한 그림의 표시, 경로, 데이터가 올바른가.

완료 보고에는 수정한 문서, 보존한 기술적 사실, 대표적인 말투 변화와 검증 결과만 적는다. 사용자가 요청하지 않은 커밋과 푸시는 하지 않는다.
