# bebeis 기술 글 말투 기준

## 목소리

글의 중심에는 기술보다 판단하는 개발자가 있다. 기술 선택을 정답처럼 선언하지 않고, 당시 요구사항과 팀 상황에서 왜 그 선택을 했는지 적는다.

- 기본 종결은 평어체다: `~다`, `~했다`, `~라고 생각했다`, `~라고 판단했다`.
- 개인 판단은 숨기지 않는다: `나는`, `우리 팀은`, `내 경험상`.
- 확신의 범위를 드러낸다: 사실은 단언하고, 선택과 해석은 판단으로 적는다.
- 엄숙한 보고서보다 개발자가 경험을 정리한 글에 가깝다.
- 가벼운 표현은 제한적으로 허용한다: `사실`, `다만`, `물론`, `좀`, 짧은 괄호, 드문 `ㅎㅎ`.

작성자의 말투는 문법 오류가 아니라 판단을 드러내는 방식에서 나온다. 오탈자, 잘못된 띄어쓰기, 영어 대소문자 혼용은 고친다.

## 문장 구성

가장 자주 쓰는 흐름은 다음과 같다.

1. 당시 조건이나 관찰을 적는다.
2. 가능한 선택지를 짧게 비교한다.
3. 선택한 이유와 감수한 비용을 적는다.
4. 필요한 경우에만 개인적인 판단으로 닫는다.

네 단계를 매번 형식적으로 채우지는 않는다. 두세 문장으로 끝낼 수 있으면 짧게 끝낸다.

문장 길이는 섞는다. 결론은 짧게 쓰고, 이유와 조건이 붙는 문장은 조금 길어도 된다. 모든 문장을 비슷한 길이로 자르면 AI가 요약한 글처럼 보인다.

## 자주 쓰는 표현의 경계

### 사실

앞선 통념이나 기대와 실제 판단이 다를 때 쓴다. 단순 문두 장식으로 반복하지 않는다.

### 다만과 물론

선택의 비용이나 예외를 인정할 때 쓴다. 장단점을 억지로 균형 있게 보이게 하려고 넣지 않는다.

### 생각했다와 판단했다

팀 상황, 설계 선택, 미래 계획처럼 정답이 아닌 부분에 쓴다. 측정 수치나 코드 동작까지 `생각한다`로 흐리지 않는다.

### 괄호와 ㅎㅎ

본문을 끊지 않아도 되는 개인 경험이나 짧은 농담에만 쓴다. 장애 분석, 성능 수치, 실패 결과에는 사용하지 않는다.

## 기술 글의 구조

- 제목과 소제목은 `문제`, `조회 구조`, `트랜잭션 경계`, `측정 결과`처럼 명사형을 우선한다.
- 문제는 현상과 비용을 적는다. `문제가 발생했다`라고 예고하지 않는다.
- 해결은 선택한 구조와 이유를 적는다. `해결했다`는 선언보다 코드와 동작을 보여준다.
- 결과는 측정값과 관찰을 적는다. 수치가 없으면 좋아졌다고 단정하지 않는다.
- 한계와 후속 선택은 실제로 확인된 내용만 적는다.
- 버전별 설명은 시간 순서를 유지하되, 독자가 앞에서 읽은 설명을 반복하지 않는다.

## 변환 예시

### 보고서체

`인덱스를 사용한 뒤에도 느렸던 게시글 목록 조회를 분석하고, 행 조립 시점과 COUNT 범위를 차례로 개선한 사례입니다.`

### 작성자 말투

`게시글 목록 조회에 인덱스를 적용했지만 여전히 느렸다. 행을 조립하는 시점과 COUNT 범위를 차례로 바꿔봤다.`

---

### 작위적인 서사

`여기서 문제가 발생했다. 과연 Redis를 도입하면 이 문제를 해결할 수 있을까?`

### 작성자 말투

`앞쪽 페이지는 같은 ID 구간을 계속 조회했다. 이 구간만 Redis에 캐시하기로 했다.`

---

### 추상적인 요약

`이를 통해 성능과 정합성을 모두 확보할 수 있었습니다.`

### 작성자 말투

`표시값은 Redis 전체 카운터만 읽게 했다. 체크포인트 중에도 조회수가 역행하지 않았다.`

---

### 과도한 단정

`Virtual Thread가 가장 우수한 해결책입니다.`

### 작성자 말투

`이 측정에서는 V3가 V2와 처리량은 비슷했고 Platform Thread를 약 42% 적게 사용했다. 그래서 현재 구조에는 Virtual Thread와 세마포어 조합을 선택했다.`

## 보존 대상

다음 항목은 말투보다 우선한다.

- 벤치마크 수치와 단위
- 테스트 환경과 측정 조건
- 기술적 인과관계와 실패 결과
- API, 클래스, 메서드, 테이블, 컬럼, 키 이름
- Markdown 링크와 이미지 URL
- 버전 이름과 개선 순서
- 코드 블록, 명령어, 설정값

문장이 어색하더라도 의미를 확신할 수 없으면 임의로 매끄럽게 만들지 않는다. 코드나 원문 블로그를 확인하고, 확인할 수 없으면 표현만 최소한으로 고친다.
