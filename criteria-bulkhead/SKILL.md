# 기준과 격벽 — 복잡한 문제의 시스템적 분석

## 왜 문제 정의부터 시작하는가

복잡한 문제는 하나의 현상이 아니다. 사용자가 본 지연, 운영자가 본 오류율, DB의 경합, 재시도가 만든 증폭은 같은 사건의 서로 다른 단면일 수 있다. 반대로 동시에 나타났다는 이유만으로 같은 원인인 것도 아니다.

해결책부터 고르면 익숙한 기술에 문제를 끼워 맞추게 된다. 먼저 **원하는 상태와 실제 상태의 차이**, 그 차이가 중요한 이유, 관측된 증거와 아직 모르는 것을 고정하라. 문제를 잘 정의한다는 것은 문장을 멋지게 쓰는 일이 아니라, 어떤 원인은 포함하고 어떤 원인은 분리하며 무엇으로 해결 여부를 판정할지 정하는 일이다.

- **기준**: 문제를 비추는 관점이자 지켜야 할 불변식·한계·품질 속성이다. 모든 기준을 같은 깊이로 적용하지 말고 위험이 큰 기준을 선택해 파고든다.
- **격벽**: 서로 섞이면 잘못된 결론을 만드는 경계다. 현상/원인/해결, 읽기/쓰기, 정상/과부하, 데이터 권위, 시간 구간, 소유권, 실패 도메인, 사실/추론을 분리한다.
- **해결안**: 특정 원인이나 제약에 개입하는 가설이다. 얻는 것뿐 아니라 해결하지 않는 것과 새로 만드는 문제까지 포함해야 완성된다.

## 절대 섞지 말아야 할 것

- 관측된 **현상**과 설명을 위한 **원인 가설**을 분리하라.
- 원인과 그것을 가능하게 한 **구조적 조건**을 분리하라. 직접 원인을 제거해도 조건이 남으면 형태만 바꿔 재발한다.
- 사실, 추론, 가정, 미확인을 문장마다 구분하라. 자료가 없으면 숫자를 만들지 말고 필요한 계측이나 실험을 제안하라.
- 평균과 꼬리 지연, 정상 부하와 폭주, 읽기와 쓰기, 논리적 성공과 durable commit을 분리하라.
- 컴포넌트 경계와 실패 경계를 같다고 가정하지 마라. 하나의 요청·큐·DB·외부 의존성이 여러 컴포넌트의 실패를 묶을 수 있다.
- 해결안의 목적과 구현 수단을 분리하라. "Redis/Kafka/샤딩을 도입한다"는 해결안이 아니라 수단이다.

## 작업 순서

순서를 지키되, 근거가 바뀌면 앞 단계로 돌아가 문제 정의를 갱신하라.

### 1. 문제를 한 문장으로 고정하라

다음을 포함해 작성하라.

> [누구/무엇]이 [조건·부하·시간]에서 [기대 상태]여야 하지만 [관측 상태]이며, [영향]이 발생한다. [지표·재현·로그]로 해결 여부를 판정한다.

곧바로 아래를 덧붙여라.

- 왜 중요한가: 사용자·비즈니스·운영 영향, 빈도, 지속 시간, blast radius, 재발성, 비가역성, 기회비용
- 범위: 포함/제외하는 흐름, 사용자, 데이터, 시간 구간, 배포 버전, 의존 시스템
- 증거 상태: 확인된 사실 / 합리적 추론 / 가정 / 미확인
- 성공 기준: 현재값과 목표값, 정확성 조건, SLO, 허용 가능한 손실·지연·비용

입력에 근거가 부족해도 분석을 멈추지 마라. 가장 작은 가정을 명시해 잠정 분석하고, 결론을 바꿀 핵심 질문과 계측을 함께 남겨라.

### 2. 현재 시스템의 실제 동작을 복원하라

컴포넌트 목록이 아니라 **요청·데이터·상태·시간·소유권의 흐름**을 따라가라.

1. 입력이 어디서 오고 어떤 순서로 처리되는지 추적하라.
2. 상태가 어디서 생성·변경·복제·캐시·삭제되는지 추적하라.
3. 각 단계의 데이터 권위와 쓰기 주체를 표시하라.
4. 동기/비동기, 트랜잭션, 큐, 네트워크, 외부 I/O 경계를 표시하라.
5. 정상 경로와 timeout·부분 성공·중복·재시작·재시도 경로를 함께 복원하라.

코드·로그·메트릭·트레이스·스키마가 있으면 직접 확인하라. 문서와 실제 동작이 다르면 차이 자체를 분석 대상으로 삼아라. 흐름이나 실패 전파가 글로 불분명하고 경계가 셋 이상이면 가장 작은 Mermaid 흐름도나 시퀀스 다이어그램을 사용하라.

### 3. 관련 기준을 선택해 깊게 분석하라

이 단계에서 [`references/analysis-lenses.md`](references/analysis-lenses.md)를 읽어라. 모든 항목을 기계적으로 나열하지 말고 다음처럼 선택하라.

- 문제와 직접 연결된 **주 기준** 2~4개를 깊게 분석하라.
- 해법 때문에 악화될 수 있는 **교차 기준**을 추가하라.
- 나머지는 관련 없음 또는 근거 부족으로 짧게 처리하라.
- 각 기준을 수치, 불변식, 실패 조건, 시간축, 자원축으로 구체화하라.

예를 들어 "성능"에서 멈추지 말고 읽기/쓰기, 요청 크기와 패턴, CPU/메모리/디스크/네트워크, 직렬화, lock 경합, 큐 대기, throughput과 p50/p95/p99, burst와 steady state로 내려가라. "정합성"에서도 강함/최종적이라는 라벨만 붙이지 말고 어떤 데이터의 어떤 불변식을 누가 언제까지 관측해야 하는지, 충돌 시 누가 승자인지, stale read가 실제로 허용되는지를 밝혀라.

CS 이론은 이름을 붙이기 위해 사용하지 마라. 큐잉, 지역성, 경합, 격리 수준, 멱등성, quorum, backpressure 같은 동작 원리가 관측 현상과 해법을 어떻게 잇는지 설명하라. 전제와 적용 한계를 함께 적어라.

### 4. 인과와 실패 지도를 작성하라

하나의 root cause를 서둘러 선언하지 마라. 다음 층을 분리하라.

- **Trigger**: 이번 사건을 시작한 변화나 입력
- **Direct cause**: 현상을 직접 만든 메커니즘
- **Contributing conditions**: 임계점, 데이터 분포, 경합, 결합도처럼 가능성을 키운 조건
- **Amplifier**: 재시도, fan-out, 캐시 미스, backlog처럼 피해를 증폭한 요인
- **Detection/recovery gap**: 늦게 알거나 오래 복구하게 만든 조건

각 외부 I/O, 저장, 큐, 캐시, 락, 리더 선출, 배포 전환에서 "여기서 실패하면 무엇이 남고, 누가 재시도하며, 중복·유실·순서 역전·오염이 어디까지 전파되는가"를 물어라. 공통 원인과 연쇄 실패를 찾고, 격벽이 이미 있는 지점과 없는 지점을 표시하라.

원인 후보마다 이를 지지하는 증거, 반증할 관측, 확신도를 남겨라. 상관관계를 인과로 단정하지 마라.

### 5. 해결안을 원인에 매핑하라

최소한 다음 범주의 후보를 검토하되 억지로 개수를 채우지 마라.

- 즉시 피해를 제한하거나 되돌리는 완화책
- 직접 원인에 개입하는 교정책
- 실패 전파를 끊거나 여유를 만드는 구조 개선
- 관측·운영·복구 능력을 높이는 안전장치
- 아무것도 바꾸지 않고 위험을 수용하는 선택

이 단계에서 [`references/solution-evaluation.md`](references/solution-evaluation.md)를 읽어라. 모든 후보에 대해 반드시 답하라.

1. 정확히 어떤 문제·원인·제약을 해결하는가?
2. 어떤 메커니즘으로 해결하는가?
3. 무엇을 얻고, 어떤 조건에서만 유효한가?
4. 무엇은 해결하지 못하는가?
5. 어떤 새 문제·실패 모드·운영 비용을 만드는가?
6. 도입·마이그레이션·롤백 중 무엇이 실패할 수 있는가?
7. 어떤 지표·테스트·실험으로 효과와 부작용을 확인하는가?

### 6. 선택하되 정답처럼 말하지 마라

후보를 단일 종합 점수로 숨기지 말고 중요한 기준별로 비교하라. 현재 제약과 우선순위에서 추천안을 제시하고, 그 선택이 뒤집히는 조건을 함께 적어라.

- 지금의 추천과 이유
- 선행 조건과 단계적 적용 순서
- 보호 장치, 중단 조건, 롤백 경로
- 남는 위험과 명시적으로 수용한 부채
- 재검토 시점과 임계값

정보가 부족해 선택할 수 없다면 막연히 "더 알아봐야 한다"고 끝내지 마라. 가장 값싼 판별 실험, 필요한 표본과 지표, 각 결과가 어느 선택으로 이어지는지 제시하라.

### 7. 검증 가능한 다음 행동으로 닫아라

설계안만 남기지 말고 다음 행동을 위험순으로 제시하라.

1. 계측 또는 재현으로 가장 큰 불확실성을 줄여라.
2. 실패 주입·부하·동시성·복구 테스트로 메커니즘을 검증하라.
3. 작은 범위에서 canary, shadow, dual-read/write, feature flag 등으로 적용하라.
4. 성공·중단 지표를 관찰하고 문제 정의와 해법을 갱신하라.

사용자가 구현까지 요청했다면 여기서 멈추지 말고 저장소 규약을 확인한 뒤 가장 작은 검증 슬라이스를 구현하라. 요구사항을 기능으로 만드는 작업에는 `concept-bulkhead`를 이어서 적용하라.

## 응답 형식

문제 규모에 맞게 다음 뼈대를 축약하거나 확장하라.

1. **문제 정의와 중요성**
2. **사실·가정·미확인**
3. **현재 동작과 경계**
4. **기준별 분석** — 주 기준부터
5. **인과·실패 지도**
6. **해결안별 효과와 대가**
7. **추천, 남는 위험, 뒤집히는 조건**
8. **검증과 다음 행동**

긴 체크리스트보다 핵심 인과관계를 먼저 말하라. 심각도와 확신도를 구분하고, 숫자는 단위·기간·백분위·부하 조건을 붙여라. 해결안이 하나뿐이어도 대안인 "현상 유지"와 비교해 선택의 대가를 드러내라.

## 하지 말아야 할 것

- 문제 정의 전에 아키텍처나 제품 이름부터 제안하지 마라.
- 모든 관점을 동일한 분량으로 채워 분석한 척하지 마라.
- "확장 가능하다", "고가용성이다", "eventual consistency면 된다"처럼 대상·조건·수치 없는 표현을 쓰지 마라.
- 재시도·캐시·복제·비동기화를 공짜 개선으로 취급하지 마라. 각각 부하 증폭, 무효화, stale state, 중복·순서·복구 문제를 만든다.
- 정상 성공 경로만 그리지 마라. 부분 실패와 복구 후 상태까지 추적하라.
- CAP, ACID, SOLID 같은 이름만으로 결론을 정당화하지 마라.
- 현재 규모와 변경 비용을 무시한 미래 확장을 설계하지 마라.
- 추천안의 미해결 영역과 되돌릴 조건을 숨기지 마라.

## 다른 스킬과의 경계

- `criteria-bulkhead`: 무엇이 문제인지, 왜 생기는지, 어느 해결안이 어떤 대가를 갖는지 분석하라.
- `concept-bulkhead`: 선택한 요구사항과 해법을 테스트와 코드로 구현하며 개념·참조 경계를 발견하라.

둘 다 필요하면 `criteria-bulkhead`로 고위험 불확실성과 선택 기준을 좁힌 뒤, `concept-bulkhead`로 가장 작은 구현과 검증을 시작하라. 분석 문서를 완벽한 청사진으로 고정하지 마라. 구현과 계측이 가정을 반박하면 문제 정의와 결정을 갱신하라.
