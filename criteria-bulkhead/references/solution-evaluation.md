# 해결안 평가와 의사결정

## 1. 해결안 단위

제품이나 패턴 이름이 아니라 **개입 대상 + 메커니즘 + 적용 범위**로 해결안을 써라.

- 나쁨: `Redis를 도입한다.`
- 좋음: `반복 조회되는 불변 메타데이터를 TTL 캐시에 두어 DB read QPS를 줄인다. 변경 시 무효화가 지연될 수 있으므로 30초 stale read를 허용하는 화면에만 적용한다.`

한 후보가 여러 원인을 해결한다고 주장하면 메커니즘을 각각 설명하라. 설명하지 못하면 후보를 나누어라.

## 2. 후보별 카드

각 후보를 아래 형식으로 기록하라.

### 해결안: [개입을 드러내는 이름]

- **대상 문제**: 해결하려는 현상, 직접 원인, 구조적 조건
- **메커니즘**: 상태·제어·자원 흐름이 어떻게 바뀌어 문제가 줄어드는가
- **얻는 것**: 기준별 개선과 예상 크기
- **유효 조건**: workload, 데이터 분포, 허용 stale, 운영 능력 등 전제
- **해결하지 않는 것**: 범위 밖 원인과 남는 현상
- **새 문제**: 새 실패 모드, 정합성·지연·비용·복잡성·보안·운영 부담
- **실패 지점**: 도입, 정상 운영, 과부하, 의존성 장애, 복구, 롤백
- **가역성**: 중단·rollback 가능 여부와 비가역 데이터 변경
- **검증**: 실험, 테스트, 지표, 성공·중단 기준
- **결정 신뢰도**: 확인된 근거와 핵심 미확인

## 3. 비교 원칙

모든 차원을 하나의 점수로 합치지 마라. 중요한 기준을 행으로, 후보를 열로 두고 실제 차이를 짧게 비교하라.

| 기준 | 현상 유지 | 후보 A | 후보 B |
|---|---|---|---|
| 직접 원인 제거 |  |  |  |
| 정합성 영향 |  |  |  |
| p99/처리량 영향 |  |  |  |
| 장애 전파·복구 |  |  |  |
| 도입·롤백 위험 |  |  |  |
| 운영 복잡성 |  |  |  |
| 비용 |  |  |  |
| 유효 조건 |  |  |  |

문제와 무관한 행은 빼고, 보안·마이그레이션·사용자 영향처럼 중요한 행을 추가하라. `높음/중간/낮음`만 쓰지 말고 가능한 경우 수치나 메커니즘을 적어라.

## 4. 시간축으로 분리

완화와 근본 개선을 경쟁 대안처럼 취급하지 마라.

- **지금**: blast radius를 줄이고 복구하라. feature off, rate limit, rollback, queue drain처럼 빠르고 가역적인 조치를 우선하라.
- **다음**: 직접 원인을 교정하고 계측·테스트를 보강하라.
- **이후**: 재발 조건과 실패 전파를 줄이는 구조 변경을 검토하라.

각 단계가 다음 단계를 불필요하게 만들거나 방해하는지 확인하라. 임시 완화책에는 제거 조건과 소유자를 둬 영구 부채가 되는 것을 막아라.

## 5. 마이그레이션도 하나의 분산 시스템으로 분석

최종 구조만 평가하지 말고 구·신 시스템이 공존하는 기간을 별도 문제로 보라.

- 데이터 복사 중 source of truth는 어디인가?
- dual-write가 한쪽만 성공하면 어떻게 복구하는가?
- backfill과 실시간 쓰기의 순서·충돌은 어떻게 다루는가?
- shadow/dual-read 차이를 어떻게 비교하고 개인정보를 보호하는가?
- mixed-version client와 rollback이 가능한가?
- cutover 기준, 중단 조건, 되돌릴 수 없는 시점은 무엇인가?

## 6. 판별 실험

비싼 구현 전에 후보를 가르는 가장 작은 실험을 선택하라.

- 프로파일·트레이스로 service time과 queue wait를 분리한다.
- 대표 데이터 분포로 부하 테스트해 hot key와 tail latency를 확인한다.
- concurrency test로 lost update·duplicate·ordering 가설을 재현한다.
- dependency에 지연·timeout·부분 실패를 주입해 증폭과 복구를 본다.
- production traffic을 쓰지 않는 shadow 경로로 결과 차이를 비교한다.
- 작은 tenant/region/canary에 적용해 성공·중단 지표를 관찰한다.

실험마다 `어떤 결과면 어떤 가설을 기각하며 어느 후보를 선택하는가`를 미리 써라. 결과를 본 뒤 기준을 바꾸는 일을 줄여라.

## 7. 추천문 형식

다음 구조로 결론을 써라.

> 현재 [제약/우선순위]에서는 [후보]를 추천한다. [메커니즘]으로 [핵심 문제]를 줄이면서 [중요 기준]을 지킬 수 있기 때문이다. 대신 [미해결 영역/새 위험]을 수용한다. [관측값/규모/조건]이 [임계값]을 넘거나 [가정]이 틀리면 [다른 후보]로 결정을 뒤집는다. 먼저 [가장 작은 실험/단계]로 검증하고 [중단·롤백 조건]을 적용한다.

정답이라고 선언하지 마라. 현재 정보와 제약 아래에서의 선택임을 밝히되, 모호한 양비론으로 책임을 피하지도 마라.

## 8. 자주 놓치는 대가

- 캐시: invalidation, stampede, stale read, cold start, 메모리·운영 비용
- 비동기화: 중복, 순서, backlog, 사용자에게 보이는 중간 상태, replay·DLQ 운영
- 재시도: 부하 증폭, 중복 side effect, timeout budget 소진
- 복제: replication lag, failover, split-brain, write latency, 비용
- 샤딩: 키 선택, hot partition, cross-shard query·transaction, 재샤딩
- 배치: 처리량 이득과 대기 시간, 부분 실패, 큰 재처리 단위
- 락: 정확성 이득과 경합·deadlock·tail latency·가용성
- denormalization: 읽기 이득과 write amplification·동기화·backfill
- managed service: 운영 절감과 quota, egress, 종속성, 제어권 감소
- 추가 추상화: 변경 격리 이득과 디버깅·학습·호출 경로 복잡성

이 목록을 자동으로 복사하지 말고 선택한 해결안에 실제로 생기는 대가만 구체화하라.
