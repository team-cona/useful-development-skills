# 개념과 격벽 — 구현 우선 개발
 
## 왜 이 순서인가
 
설계를 잘하는 방법은 설계를 하지 않는 것이다. 요구사항은 항상 변하고("요구사항은 변한다"는 사실만 변하지 않는다), 완벽한 설계는 발전 없이 죽어가는 서비스에서만 가능하다. 우리가 만드는 건 소프트웨어다 — 하드웨어나 롯데타워가 아니므로, 변경된 요구사항을 수용할 수 있는 구현을 계속 만들어가는 것이 곧 설계다.
 
개념과 격벽은 다이어그램이 아니라 **코드로 존재한다.** 발표 자료의 도식은 설명을 위한 장치였을 뿐이다. 따라서 개념도는 구현의 **산출물**이지 입력물이 아니다.
 
- **개념**: 소프트웨어의 비즈니스를 지탱하는 것. 클래스로 존재한다.
- **격벽**: 개념 간 접근을 제어·통제하는 방화벽. 코드에서는 참조 규칙으로 존재한다.
- **상태**: 개념이 *가지는* 것(모집중/완료, 대기/수락). 개념이 아니다.
- **행위**: 개념에 *속한* 동작(신청하기, 수락, 납부). 개념이 아니다. 단, 상태·행위가 개념인지 착각인지는 케이스마다 다르므로 머리가 아니라 코드로 검증한다.
- **무개념**: 외부 연동사, OAuth, LLM API, 파일 스토리지, 모니터링, 라이브러리 등. 우리 의도와 무관하게 변하므로 지켜야 할 개념이 될 수 없다. 참조 불가의 벽으로 격리한다.
## 가장 흔한 실수 — 이것부터 차단하라
 
PRD를 받으면 "개념 후보 추출 → 개념/상태 분류 → 생명주기 그룹핑 → 개념도 스케치 → 그 다음 구현"의 순서로 정리하고 싶어진다. **그게 바로 이 방법론이 하지 말라는 '분석하고 설계하고 나서야 구현'이다.** 그럴싸해 보여서 더 위험하다. 분류표와 개념도는 5단계에서, 구현된 코드를 보고 그린다. 구현 전에 세운 개념 가설(예: "A와 B는 분리해야 할 것 같다")은 청사진이 아니라 검증 대상일 뿐이다 — 코드가 반박하면 버린다.
 
## 작업 순서 (이 순서를 바꾸지 않는다)
 
### 1. 요구사항을 분석·이해한 뒤, 구현을 먼저 진행한다
 
이해의 산출물은 문서가 아니라 **오늘 짤 코드**다.
 
- 프로젝트에 코드 컨벤션 문서가 있으면 먼저 읽는다. 모듈 구조·레이어·네이밍은 설계가 아니라 팀 규약이므로 고민 없이 그대로 쓴다.
- 요구사항을 먼저 짧은 자연어 흐름으로 푼다. **무엇이 어떤 순서로 생기거나 바뀌는지, 중간 단계가 실패하면 무엇이 남아야 하는지**까지 한두 문장으로 말한다. 이 흐름은 컴포넌트 목록을 만들기 위한 설계 문서가 아니라 바로 테스트 이름으로 옮기기 위한 작업 메모다.
- **테스트를 먼저 쓴다.** 요구사항의 규칙과 엣지 케이스가 그대로 첫 테스트 이름이 된다 ("정원 초과 시 수락 불가", "중복 요청은 한 번만 처리"). 첫 커밋은 개념도가 아니라 테스트여야 한다.
- 실패하는 테스트가 요구할 때 개념 클래스(도메인 객체)와 개념적인 도구를 만든다. 이름은 Reader·Manager 같은 접미사부터 고르지 말고 요구사항 문장의 역할에서 얻는다. 프레임워크·트랜잭션 같은 구현 메커니즘은 이름에 드러내지 않는다.
- 개념 객체는 **이번 행위가 문제를 해결하는 데 필요한 값과 규칙**을 담아 만든다. 기존 모델이 있다는 이유만으로 재사용하지 않는다. 여러 곳에서 쓰인다는 사실도 동일한 개념이라는 증거가 아니다. 의미·불변식·수명과 변경 이유가 실제로 같을 때만 재사용한다. 이번 범위 밖에서 다른 팀원이 만든 모델은 아직 다른 가설일 수 있으므로, 행위에 더 정확한 모델이 필요하면 별도로 만든다.
- 작은 개념 객체는 더 큰 개념 객체의 일부로 조합할 수 있다. 처음부터 모든 값을 하나의 범용 모델에 모으지 말고, 테스트에서 함께 움직이는 값과 규칙이 확인될 때 조합한다.
- 미결정 사항(TBD)은 지금 **최소한으로** 결정하고 진행한다. 방장을 필드로 둘지 레코드로 둘지 같은 고민은 그냥 단순한 쪽으로 시작한다 — 틀렸다면 나중에 코드가 말해준다.
- 잘못된 요구사항, 변경되는 요구사항, 모호한 부분은 반드시 나온다. 일정 내에서 이것도 수용하며 구현을 계속 진행한다.
- 슬라이스는 제품 흐름 순서로, PRD에 단계별 범위(런치 1단계 등)가 있으면 그 최소 범위만 잡는다.
### 2. 구현하면서 무엇이 핵심이고 중심인지 이해한다
 
분석표를 미리 만드는 게 아니라, 구현 중에 코드가 보내는 신호로 파악한다. 한 메서드에 여러 개념의 일이 뭉치기 시작하거나, 특정 클래스가 사방에서 주입되거나, 테스트를 쓰다가 "이 둘은 다른 것이구나"를 느끼는 순간들이 그 신호다.

이때부터 **설계 산출물을 구현과 함께 누적한다.** 산출물은 구현을 시작하기 위한 승인 문서가 아니라, 테스트와 코드에서 확인된 사실을 보존하는 작업 기록이다. 첫 테스트 전에는 요구사항과 당장 구현할 자연어 흐름만 적고, 개념·컴포넌트·인프라 구조는 각 슬라이스가 동작한 뒤 갱신한다. 구현된 흐름에 의미 있는 호출 순서·분기·경계가 있으면 같은 문서에 작은 Mermaid 시퀀스 다이어그램도 갱신한다. 저장소에 `_workspace`가 있으면 그 아래에 두고, 없으면 프로젝트 문서 관례를 따른다.
 
구현이 어느 정도 쌓였을 때, 그리고 코드 리뷰를 할 때 `references/signals.md`를 읽고 진단 도구(이름 바꾸기 테스트, 대출·연체 패턴, 생명주기 표 등)를 적용한다.
 
레거시 코드라면 이 단계 이전에 레거시 현황 이해가 선행된다.
 
### 3. 핵심을 최대한 순수하게 — 의존을 끊어내며 계속 구현한다
 
- 무개념(외부)은 참조 불가의 벽 밖으로. 외부 데이터가 필요하면 벽 바깥의 수집·정제 영역에서 긁어와 내부 개념의 데이터로 적재한다. 코어는 외부의 존재를 모른다.
- 원칙으로 강제하지 말고 **테스트가 강제하게 하라.** "외부 호출이 실패해도 코어 처리는 유지된다" 같은 테스트를 짜려는 순간, 외부가 핵심 로직 한가운데 있으면 테스트를 못 짠다. 그래서 밀어낼 수밖에 없고, 그 밀어낸 자리가 격벽이다.
- 순수 계산 로직은 프레임워크 없는 일반 클래스로 둔다. 테스트가 쉬워진다는 사실 자체가 그것이 순수한 핵심이라는 증거다.
- 초기에 구현하며 생각한 것들은 분명히 바뀐다. 1단계의 결정이 뒤집히는 건 실패가 아니라 이 방법이 작동하고 있다는 신호다.
### 4. 요구사항이 충족되고 기본 테스트가 성공한다
 
범위 내 요구사항 전부가 돌아가고, 엣지 케이스(중복 방지, 동시성, 멱등)가 테스트로 존재하는 상태. 이 테스트 묶음이 곧 "반복할 수 있는 환경"이며, 이후 개념을 다시 자르고 붙이는 리팩토링을 겁 없이 하게 해주는 안전망이다.
 
### 5. 이제야 개념과 격벽을 개념도에 그린다 — 구현된 코드 기준으로
 
- 머릿속 계획이 아니라 실제 패키지·클래스·의존 방향을 보고 그린다. 그래서 그리는 행위 자체가 진단이 된다.
- **상태는 그리지 않는다. 개념만 그린다.** 상태를 다 표기하면 개념 정의와 격벽 구성이 복잡해진다.
- 그리다가 이상한 화살표가 보이면 — 무개념이 코어로 침투해 있거나, 한 개념이 사방에서 참조되거나 — 코드로 돌아가 고치고 다시 그린다.
- 개념이 많으면 계층을 나눈다: 1급(비즈니스의 축) / 2급 / 무개념. 모든 것이 개념이 되지는 않는다.
- 구현 중 누적한 설계 산출물을 실제 코드 기준으로 정리한다. 잠정 가설과 폐기된 구조는 걷어내고, 현재 구현과 남은 TBD를 분리한다.
### 6. 팀 내(개발·기획·디자인)에 공유하여 인식을 맞춘다
 
개념도가 팀의 공용 언어가 된다. 기획 문서에서 섞여 쓰이는 용어를 코드의 개념과 정렬하고, 남은 TBD가 결정될 때 이 그림 위에서 영향 범위를 대화한다. 다음 단계 요구사항이 들어오면 1~5를 다시 돈다.

## 설계 산출물 — 구현을 따라가는 핵심 기록

산출물은 코드 목록이나 상세 구현 해설이 아니라, 요구사항이 어떤 개념과 시스템 구조로 실현됐는지 보여준다. 기능 규모에 맞게 다음 순서에서 필요한 항목만 남긴다.

1. **요구사항** — 구현 범위와 중요한 불변식·보존 원칙. 화면 문구나 당연한 CRUD 설명은 줄인다.
2. **개념과 격벽** — 핵심 개념, 각 개념의 수명과 소유 규칙, 서로를 아는 방향, 상태·행위·무개념과의 구분. 기존 모델 재사용 여부는 이름이나 필드 모양이 아니라 이번 행위에서의 의미·불변식·수명으로 판단하고, 작은 개념이 큰 개념을 이루는 조합이 중요하면 함께 기록한다.
3. **비즈니스 흐름** — 무엇이 어떤 순서로 생기고 바뀌는지, 성공 결과, 각 단계 실패 시 무엇이 남고 무엇은 실행되지 않는지.
4. **구현 컴포넌트** — 흐름을 실현하는 개념적인 도구와 커밋 단위. 단순 위임·매퍼·모든 클래스를 나열하지 않고 경계를 결정하는 컴포넌트만 적는다.
5. **시스템 흐름** — 클라이언트에서 서버를 거쳐 DB·파일 저장소·캐시(Redis 등)·메시지 브로커(Kafka 등)·외부 API까지 데이터와 제어가 이동하는 방향. 실제로 필요한 것만 포함하고, 도입하지 않기로 한 기술은 그 선택이 중요한 경우에만 이유를 적는다.
6. **결정과 TBD** — 구현으로 확정된 선택, 아직 테스트하지 않은 실패 정책, 다음 요구사항에서 재검토할 조건.

각 테스트·구현 슬라이스가 끝날 때 해당 부분만 짧게 갱신한다. 성공 경로만 그리지 말고 외부 I/O 전후, 트랜잭션 전후, 비동기 전달 전후의 실패 결과를 반드시 확인한다. 문서와 코드가 다르면 문서를 정답으로 밀어붙이지 말고 테스트와 구현을 다시 확인해 둘을 맞춘다.

비즈니스 흐름이나 시스템 흐름을 기록했다면, 호출 순서·분기·커밋 또는 시스템 경계가 글만으로 한눈에 읽히지 않을 때 같은 문서에 **작은 Mermaid 시퀀스 다이어그램**을 함께 둔다. 시퀀스 다이어그램은 테스트와 구현에서 확인된 사실만 그리며 자연어 설명을 대체하지 않는다.

- `sequenceDiagram`의 `alt`·`else`·`opt`를 사용해 성공·실패 분기와 롤백 결과를 호출 순서 안에 표현한다.
- 참가자는 비즈니스 흐름이면 핵심 개념·컴포넌트, 시스템 흐름이면 클라이언트·서버·DB·외부 시스템처럼 해당 흐름의 경계를 드러내는 대상으로 고른다.
- 한두 단계뿐인 단순 위임은 그리지 않는다. 노드와 화살표는 핵심 경계만 남긴다.
- draw.io는 자동 산출물로 만들지 않는다. 전체 구조가 충분히 구현되어 큰 그림이 굳은 뒤, 사용자가 명시적으로 요청한 경우에만 별도 제작한다.

산출물의 상세 수준은 다음 기준으로 제한한다.

- 포함: 개념의 수명과 소유권, 참조 방향, 트랜잭션·비동기·재시도·멱등 경계, 데이터 원천, 외부 실패 후 남는 상태, 인프라 선택 이유.
- 제외: 코드 한 줄씩 풀이, 테스트 이름 전체 복사, DTO·Repository 메서드 전수 목록, 한 줄 위임이나 매핑처럼 구조 판단에 영향을 주지 않는 내용.
- 시퀀스 다이어그램은 분기·커밋 경계 또는 클라이언트·서버·저장소·외부처럼 경계가 셋 이상 얽혀 호출 순서를 더 명확히 보여줄 때만 가장 작은 형태로 사용한다.
 
## 격벽의 코드 규칙
 
프로젝트에 컨벤션 문서가 있으면 **그 문서가 격벽의 구체 규칙이다** — 그것을 따른다. 없으면 기본 규칙:
 
- 다른 개념의 Service를 직접 참조하지 않는다. 재사용이 필요하면 구현 컴포넌트(Reader/Manager 등) 단위로 참조한다.
- 여러 개념의 조합이 필요한 화면·응답은 조립 지점(Assembler/Facade)에서 조합한다.
- Entity(저장 기술)를 개념 위로 노출하지 않는다. 개념 클래스와 API·DB는 격리되어 있다 — 그래서 API 스펙은 mock으로 먼저 뽑아 넘기고 내실을 다지는 것도 가능하다.
- 무개념(외부)은 별도 모듈로 두고, 코어는 그 존재를 모르게 한다. 같은 테이블을 써야 한다면 영역별로 엔티티를 분리해 쓰기 권한을 통제할 수 있다.
## 응답 방식 — 사용자가 설계를 먼저 요구할 때
 
- "설계해줘", "개념도 그려줘", "구조 잡아줘"를 받으면: 구현이 이미 있는지 확인한다. 구현된 코드가 있으면 그 코드를 기준으로 그린다(5단계). 구현 전이면 코딩 시작용 러프 스케치를 **짧게만** 제시하고, 거기서 멈추지 말고 첫 테스트 코드를 함께 제시하며 구현으로 넘어간다.
- 하지 말아야 할 말을 하지 않는다: "요구사항이 완벽해야 설계할 수 있다", "우리 설계에서 그건 개발 못 한다."
- 과도한 설계를 제안하지 않는다. 지금 요구에 없는 확장성·추상화·패턴을 미리 넣지 않는다. Out of Scope로 명시된 것은 코드에서 냄새가 나기 시작할 때 격벽으로 분리한다 (연체 패턴 — `references/signals.md` 참고).
- 기존 이론이나 용어(DDD, 디자인 패턴 등)에 기대어 정당화하지 않는다. "그건 XX가 아니다"가 아니라, 구현에서 드러난 핵심 책임과 경계가 왜 필요한지를 구체적으로 설명한다.
