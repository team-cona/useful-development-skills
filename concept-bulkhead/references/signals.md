# 구현 중 진단 신호 카탈로그
 
구현이 어느 정도 쌓였을 때, 그리고 코드 구조 리뷰를 할 때 적용하는 도구들이다. 미리 분석표로 만드는 게 아니라, 코드가 이 신호를 보낼 때 알아채는 용도다. 각 신호는 "무엇을 관찰하고 → 무엇을 의심하고 → 무엇을 해보는지"로 읽는다.
 
## 1. 이름 바꾸기 테스트
 
개념 클래스의 이름을 실제로 변경해보고 diff가 어디까지 번지는지 본다.
 
- 같은 개념 그룹의 코드(Service, 컴포넌트, 테스트)만 바뀐다 → 건강하다.
- 다른 개념의 코드까지 우르르 바뀐다 → 개념이 너무 크거나 격벽 없이 돌아다니고 있다.
- 같은 그룹이어야 할 코드가 안 바뀐다 → 개념 정의 자체가 잘못됐을 수 있다.
주기적으로 돌릴 수 있는 가장 값싼 진단이다.
 
## 2. 하나의 개념이 모든 곳에서 쓰인다 (대출 패턴)
 
대출 서비스에서 Loan 클래스 하나가 신청·실행·상환 코드 전부에 등장했다. 이름을 바꾸자 전체가 흔들렸고, 그제서야 신청·실행·상환이 행위가 아니라 대출과 동급의 개념임을 알게 됐다. 흐름으로 다시 정리하면: 신청을 통해 실행하면 결과물이 대출이고, 대출을 상환한다.
 
- 신호: 한 클래스가 거의 모든 Service에 주입된다. setup 없이는 아무 테스트도 못 짠다.
- 처방: 그 개념에서 각 사용처가 정말 필요로 하는 게 무엇인지(일정? 상태? 정원?) 좁혀보고, 행위라고 생각했던 것들이 사실 동급 개념이 아닌지 의심한다. "X의 결과물로 Y가 생긴다"(신청의 결과물로 참여자가 생긴다 등)로 흐름을 다시 말해보면 경계가 드러난다.
## 3. 상태에서 개념이 새끼친다 (연체 패턴)
 
상환에는 성공/실패 상태가 있었는데, 실패 상태 아래에서 재시도·추가 이자 로직이 계속 자라났다. 상환 개념이 영원히 끝나지 못하고 떠도는 느낌이 들어 실패 뒤에 격벽을 세워보니 — 상환은 성공/실패 상태를 내는 순간 개념적으로 역할이 끝났고, 그 이후는 연체라는 별도 개념이었다. 재시도·추가 이자는 사실 연체 납부(행위)와 연체 이자였다.
 
- 신호: 특정 상태 분기 아래의 코드가 계속 증식한다. `XxxRetryService`, `XxxFailProcessor` 같은 클래스가 원 개념 주변에 늘어난다. 한 개념이 종결되지 못하고 계속 살아있는 느낌.
- 처방: 그 상태 뒤에 격벽을 세워보고, 격벽 너머가 별도 개념인지 테스트 코드 기준으로 검토한다. 원 개념은 상태를 내는 것까지만 책임지게 한다.
- 주의: **미리 만들지 않는다.** Out of Scope인 후속 처리(제재, 정산 등)를 예상해서 개념부터 파두는 건 과도한 설계다. 코드에서 자라기 시작할 때 분리한다.
## 4. 생명주기 표 (생성·조회·수정·삭제)
 
두 개념이 같은 격벽 안에 있어야 할지 애매하면, 생성·조회·수정·삭제 각각에서 함께 움직이는지 따져본다.
 
- 상품·상품아이템·상품옵션: 생성 시점은 달라도(옵션은 선택) 조회·삭제가 함께 움직인다 → 같은 주기로 묶을 후보.
- 상품과 찜: 생성이 서로를 만나지 않고, 상품이 삭제될 때 찜을 어떻게 할지는 기획마다 다르다 → 다른 주기.
- 결제와 정산: 결제가 이미 종결된 뒤(예: 7일 후) 정산이 일어난다 → 결제 개념은 끝났고 정산은 별도 주기.
- 주문과 결제: 주문이 있다고 결제가 반드시 생기지 않는다. 주문 조회 시 결제 조회는 부가 연결 기능처럼 보인다 → 주문은 결제 전까지의 개념으로 좁힐 수 있다.
정답 찾기가 아니라 응집·결합을 느끼는 도구다. 요구사항이 바뀌면 답도 바뀐다.
 
## 5. 입출력 비대칭
 
한 개념의 컴포넌트가 처리 결과로 **다른 개념의 타입을 리턴**한다면 의심한다. (배송 예약 컴포넌트가 주문 타입이나 배송부가서비스 타입을 리턴하는 사례.)
 
- 인풋으로 상류 개념을 받는 것은 자연스럽다 — 개념의 흐름상 주문이 배송으로 넘어가는 건 현실과 같다.
- 아웃풋이 타 개념이라면: 그 컴포넌트의 소속이 잘못됐거나("주문을 만들기 위한 클래스라면 배송 개념이 아닐 수 있다"), 개념 정의가 꼬여 있다. 인풋과 아웃풋이 대칭이어야 직관적이다.
- 인터페이스로 의존 역전부터 하려 들지 않는다. 개념 정리가 먼저고, 인터페이스는 구현이 직관적으로 정리된 뒤에 뽑아도 늦지 않다.
## 6. 너무 빠른, 너무 잘게 쪼갠 분리
 
접두어만 같은 개념이 난립하면(배송, 배송부가서비스 …) 너무 빨리 쪼갠 신호다. 앞에 같은 명사가 반복되면 보통 같은 개념에 속한다.
 
- 처방: 일단 하나의 격벽 안에 함께 둔다. 격벽을 세우는 건 코드가 커져서 당위성이 생겼을 때다. 같은 격벽 안에서는 개념 간 화살표를 강제하지 않아도 된다. 나중에 은닉하거나 하위 구현 레벨로 내릴 수도 있다.
- public 메서드 수는 분리 기준이 아니다. 같은 상태·생명주기·불변식·의존성을 공유하는 행위는 한 클래스에 모은다. 세션의 열기와 닫기처럼 한 개념의 생명주기를 함께 다루는 경우가 그렇다.
- 메서드 하나뿐인 클래스도 독립된 규칙, 격벽, 커밋 단위를 소유한다면 자연스럽다. 반대로 Repository 호출을 한 줄 감쌀 뿐 새로운 규칙이나 경계를 만들지 못하면 합친다.
- 롤백·재시도 경계가 다르거나, 외부 I/O가 사이에 끼거나, 다른 개념의 정책이 자라기 시작할 때 분리를 검토한다. `1 클래스 = 1 메서드`를 목표로 기계적으로 쪼개지 않는다.
## 7. 무개념 침투
 
코어 코드에 외부 SDK, HTTP 클라이언트, 외부 응답 스키마, 저장 기술의 세부가 보이면 참조 불가의 벽이 뚫린 것이다.
 
- 처방: 외부 호출부는 벽 바깥의 수집·정제 영역(client 성격 모듈)으로 밀어내고, 외부 데이터는 긁어와 내부 개념의 데이터로 적재한다. 코어는 "깔끔한 내부 개념"만 쓴다.
- 같은 테이블을 공유해야 한다면 영역별로 엔티티를 분리해, 수집 영역만 쓰기가 가능하고 코어 영역은 읽기만 하도록 강제할 수 있다.
- 리트머스: "외부가 죽거나 스펙이 바뀌어도 코어 개념의 테스트가 그대로 통과하는가."
## 8. 테스트가 보내는 냄새
 
- setup이 비대해진다, mock 없이는 아무것도 못 돌린다 → 격벽 부재 또는 개념 오염.
- 외부(네트워크·시간·랜덤) 없이는 테스트가 불가능하다 → 무개념 침투.
- 반대로, 어떤 로직을 일반 클래스로 빼자 테스트가 갑자기 쉬워진다 → 그게 순수한 핵심이라는 증거. 그 방향으로 계속 민다.
## 9. 과도한 설계 냄새
 
- 지금 트래픽·요구에 없는 것을 위한 추상화, 설정, 확장 포인트가 코드에 있다 → 제거한다. 초당 100명이 쓰는 서비스에 10만 명용 설계를 하지 않는다.
- 요구사항에 없는 "언젠가 필요할" 개념·인터페이스를 미리 파고 있다 → 멈춘다. 설계는 필요한 만큼만.
- 자기 만족·기술 자랑·이력서용 구조가 아닌지 스스로 물어본다.

## 10. 기술적인 이름 냄새

클래스 이름이 요구사항의 역할보다 구현 방법을 먼저 설명하면 개념이 기술에 가려진 신호다.

- 신호: `Initializer`, `Committer`, `Provisioner`처럼 초기화 순서나 트랜잭션 커밋 방식을 설명하면 이름은 쉬운데, "이 도구가 업무에서 무엇을 하는가"는 다시 코드를 열어봐야 한다.
- 진단: 클래스를 요구사항 문장 안에서 소리 내어 읽는다. `MemberRegistrar가 회원을 등록한다`, `SessionAuthenticator가 세션으로 회원을 인증한다`처럼 자연스럽게 역할이 읽히는지 본다.
- 접미사 자체를 금지하지 않는다. `Processor`도 요구사항에 이름이 있는 처리 단계와 생명주기를 소유하면 정확한 이름이다. 반대로 서로 다른 잡일을 "처리"로 뭉뚱그릴 때는 책임을 다시 풀어낸다. 다른 접미사도 같은 기준으로 판단한다.
- 처방: 클래스에는 개념적인 도구, 메서드에는 업무 동사를 둔다. `MemberRegistrationCommitter.commit`보다 `MemberRegistrar.register`처럼 무엇을 하는지가 먼저 보이게 바꾼다.
