# 개발 글의 깊이: 판단, 코드, 장애

엔지니어링 글을 쓸 때 읽는다. 토스 엔지니어링 글은 해결책 소개보다 **판단하는 개발자**가 중심이고, 근거는 코드·설정·로그·측정값 같은 실물이다. 이 문서의 일부 원칙은 사용자가 쓰는 다른 개발 글쓰기 가이드(rewrite-bebeis-devlog)에서 가져와 토스 문체에 맞게 바꿨다.

## 1. 판단을 보여 주는 순서

결정 하나를 쓸 때 대체로 이 순서를 따른다. 네 단계를 매번 다 채우지는 않는다. 두세 문장으로 끝낼 수 있으면 짧게 끝낸다.

1. 당시 조건이나 관찰 (사실, 단언한다)
2. 검토한 선택지 (재료에 있을 때. 서킷 브레이커, 세마포어, 화이트리스트 같은 대안)
3. 고른 이유와 고르지 않은 이유
4. 감수한 비용

- 사실(측정값, 코드 동작)은 단언하고, 선택과 해석은 판단으로 쓴다("~라고 판단했습니다", "~쪽이 맞다고 봤습니다"). 측정값까지 "~것 같습니다"로 흐리지 않는다.
- 팀 안에서 의견이 갈렸다면 그대로 쓴다. 누가 어떤 걱정을 했고, 무엇으로 결론을 냈는지(섀도 모드, 실험, 데이터).
- 문제는 현상과 비용으로 쓴다. "문제가 발생했다"고 예고하지 않는다. 해결은 "해결했다"고 선언하지 않고 바꾼 구조와 동작을 보여 준다.

## 2. 배경지식은 다음 결정에 필요한 만큼만

- 개념 설명은 그 개념이 쓰이는 판단 바로 앞에 둔다. 글 앞쪽에 용어를 몰아 설명하지 않는다.
- 설명할 때는 사전식 정의보다 이번 결정에 필요한 것을 쓴다: 값의 범위와 단위, 비슷한 개념과의 차이, 운영에서 이어질 수 있는 문제.
- 독자가 이미 읽은 문제를 해결 절과 결과 절에서 다시 풀어 쓰지 않는다.

## 3. 코드 발췌

토스 엔지니어링 글의 54%에 코드 블록이 있다. 코드는 **문제 해결의 핵심이 코드의 흐름에 있을 때** 넣는다.

넣을 가치가 있는 것:
- 분기(캐시 hit/miss/폴백, 상태 전이), 재시도와 보상 순서
- 동시성 제어(풀, 세마포어, 락), 트랜잭션 경계
- 설정값이 판단의 핵심일 때(타임아웃, 풀 크기, 임계값)
- Before/After를 나란히 보여 줄 때

빼는 것: 로그 출력, 메트릭 계측, import, 생성자 주입, getter/setter, DTO 변환 같은 보일러플레이트.

쓰는 법:
- 코드 블록 하나에 하나의 흐름만. 설명보다 코드가 길면 줄인다.
- 코드 블록에는 언어를 적는다. 주석은 한국어로 짧게(`// 카드사별 풀이 가득 차면 바로 거절`).
- 코드 앞에 이 코드가 보여 주는 판단을 한 문장, 뒤에는 줄별 해설 대신 달라진 점이나 지키는 조건만 쓴다.
- **재료에 없는 코드를 실제 코드처럼 만들지 않는다.** 설명에 꼭 필요하면 짧은 의사 코드를 쓰되 "흐름만 단순화한 예시"라고 밝히고 `[확인 필요: 실제 코드로 교체]`를 붙인다. 그것도 어렵다면 설정 표나 상태 표로 대신한다.

## 4. 장애·문제 대응 글

- **장애가 어떻게 멈췄는지**를 원인 분석보다 먼저 한 문단으로 쓴다. 누가, 언제, 무엇으로(롤백, 설정 변경, 트래픽 차단) 멈췄는지. 재료에 없으면 `[확인 필요]`.
- 시간 순서를 지킨다. 임시 조치(장애 중)와 근본 조치(장애 뒤)를 구분한다.
- 시간축 지표 그림(대시보드 캡처나 그 자리) 하나가 있으면 좋다.
- 한계와 다음 과제는 한 곳에서만 말한다. 마무리에서 되풀이하지 않는다.

## 5. 결과

- 결과는 측정값과 측정 조건(기간, 대상, 비교 방법)으로 쓴다. 조건이 없으면 `[확인 필요: 측정 기간]`.
- 수치가 없으면 좋아졌다고 단정하지 않는다.
- 여러 요인이 섞였을 수 있으면 한 번만 짧게 밝힌다. 조심하는 말을 여러 번 겹치지 않는다.
