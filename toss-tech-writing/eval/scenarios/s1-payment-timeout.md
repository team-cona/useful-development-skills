# 재료: 결제 승인 API 타임아웃 장애 대응 (분야: 엔지니어링 / Server)
글쓴이: 토스페이먼츠 결제코어팀 Server Developer 박지훈

- 2026년 3월 금요일 저녁 7시쯤, 결제 승인 API 에러율이 평소 0.02%에서 4.8%까지 튐. 약 11분간.
- 가맹점 CS 채널에 "결제 버튼 누르면 한참 돌다가 실패해요" 문의 다수.
- 처음 의심: DB. 그런데 DB 지표 정상. CPU 40%대.
- 실제 원인: A 카드사 승인 응답이 평소 p99 300ms → 8초로 느려짐. 우리 서버는 카드사 호출에 공용 HTTP 커넥션 풀(최대 200개) 사용. A 카드사 요청이 커넥션을 잡고 안 놔줘서 풀 고갈 → 정상인 B, C 카드사 결제까지 실패.
- 타임아웃 설정은 10초였음. 카드사 정책상 승인 응답 최대 대기 권장이 10초라서 그렇게 둠.
- 첫 대응: 타임아웃을 3초로 낮춤 → 에러율은 줄었지만 A 카드사의 "늦게라도 승인된 건"이 우리 쪽에선 실패 처리 → 망취소 필요 건 37건 발생. 결국 원복.
- 진짜 문제 재정의: "느린 카드사 하나가 전체를 막는다"가 문제. 타임아웃 길이가 문제가 아님.
- 해결 1: 카드사별 커넥션 풀 분리(bulkhead). 카드사 18곳, 트래픽 비중에 따라 풀 크기 배정. 합계는 기존 200 → 260.
- 해결 2: 카드사별 동시 대기 요청 수 상한(최근 1분 p99 기반으로 동적 조정). 상한 넘으면 즉시 "잠시 후 다시 시도" 응답 + 가맹점에 카드사 지연 안내 코드 반환.
- 해결 3: 타임아웃 난 건은 실패가 아니라 "확인 중" 상태로 두고 카드사 조회 API로 30초 내 재확인 → 망취소 대상 자동 판정.
- 결과(2026년 5월 비슷한 카드사 지연 재발 시): 영향 범위가 해당 카드사 결제로만 한정. 전체 에러율 0.31% (해당 카드사 비중 6%). 망취소 수작업 0건.
- 비용/한계: 풀 18개 관리 복잡. 신규 카드사 붙일 때 풀 크기 산정 기준 필요 → 현재 반자동. 동적 상한이 너무 보수적이라 평소 피크에도 0.01% 정도 거절 발생 → 튜닝 중.
- 배운 점: 타임아웃은 "얼마나 기다릴지"가 아니라 "누구를 기다리느라 누구를 못 받는지"의 문제. 장애 격리 단위 = 외부 의존성 단위.
- 그림 후보: 공용 풀 vs 분리 풀 비교, 상태 흐름(승인요청→확인중→승인/망취소), 에러율 비교.
