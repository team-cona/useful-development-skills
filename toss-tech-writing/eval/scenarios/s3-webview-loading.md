# 재료: 토스 앱 웹뷰 첫 화면 로딩 개선 (분야: 엔지니어링 / Frontend)
글쓴이: 토스 Frontend Platform 팀 Frontend Developer 정하은

- 토스 앱 안 서비스 다수가 웹뷰(Next.js). 사용자가 홈에서 서비스 진입 시 흰 화면이 보이는 시간이 길다는 불만.
- 측정: 진입 탭 → 첫 콘텐츠 표시(FCP)까지 p75 1.9초(안드로이드 중저가 기기 p75 3.4초).
- 처음 접근: JS 번들 줄이기. 공통 번들 840KB → 610KB로 줄임(트리셰이킹, 날짜 라이브러리 교체). FCP는 고작 0.1초 개선.
- 다시 측정해보니 시간의 절반 이상이 웹뷰 생성 + 첫 HTML 요청 전 단계(네이티브 쪽 웹뷰 초기화 ~600ms, DNS/TLS ~350ms). 번들은 병목이 아니었음.
- 재정의: "웹 페이지를 빠르게"가 아니라 "사용자가 탭하기 전에 준비해두기".
- 해결 1: 홈 화면이 보일 때 자주 들어가는 상위 서비스 5개에 대해 웹뷰 인스턴스를 미리 만들어 둠(warm pool). 메모리 사용량 증가 약 38MB → 저사양 기기(RAM 4GB 이하)는 2개만.
- 해결 2: 미리 연결(preconnect)과 HTML 프리페치. 단, 개인화된 HTML은 프리페치하면 오래된 데이터 보여줄 위험 → 셸(레이아웃)만 프리페치, 데이터는 진입 후 요청.
- 해결 3: 첫 화면을 스켈레톤이 아니라 마지막으로 본 화면의 스냅샷으로 표시(30분 이내만). 
- 실패: 스냅샷 방식은 잔액 화면에서 "예전 잔액이 잠깐 보인다"는 문제 → 금액이 보이는 화면은 스냅샷 제외 규칙 추가.
- 결과: FCP p75 1.9초 → 0.7초, 중저가 안드로이드 p75 3.4초 → 1.3초. 진입 후 3초 내 이탈률 9.1% → 4.6%.
- 비용: 앱 메모리 사용 증가로 OOM 크래시율 0.02%p 증가 → warm pool 크기를 기기 메모리에 따라 동적으로 조정해서 원래 수준으로 복구.
- 배운 점: 측정 구간을 쪼개기 전엔 최적화하지 말 것. 프론트엔드 성능 문제의 절반은 웹 밖에 있었음.
- 그림 후보: 진입 타임라인 구간별 막대(웹뷰 초기화/네트워크/HTML/JS/렌더), 개선 전후 FCP 비교.
